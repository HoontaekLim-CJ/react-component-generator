# commit: 변경사항 분석 후 컨벤션 커밋

변경사항을 읽고 **논리적 단위별로** 커밋 계획을 세운 뒤, **승인을 묻지 않고 바로** 커밋한다.
대신 무엇을 어떻게 커밋했는지 결과를 분명히 보고해, 사용자가 사후에 확인하고 되돌릴 수 있게 한다.

## 1. 변경사항 수집

다음을 병렬로 실행해 현재 상태를 파악한다.

```bash
git status --porcelain=v1 -uall      # 수정·삭제·신규(untracked) 파일 전체
git diff                             # 스테이징 안 된 변경
git diff --staged                    # 이미 스테이징된 변경
git branch --show-current
git log --oneline -10                # 기존 메시지 스타일 참고
```

- 변경사항이 없으면 "커밋할 변경사항이 없습니다."라고 알리고 종료한다.
- untracked 파일은 `git diff`에 나오지 않으므로 직접 읽어 내용을 확인한다.
- 사용자가 이미 일부를 스테이징해 두었다면 그 의도를 존중해, 스테이징된 묶음을 하나의 단위 후보로 먼저 본다.
- diff가 매우 크면 `git diff --stat`으로 윤곽을 잡은 뒤 파일별로 나눠 읽는다.

## 2. 논리적 단위로 분류

"하나의 커밋 = 하나의 이유"가 기준이다. 되돌릴 때 함께 되돌려야 하는 변경을 한 단위로 묶는다.

- 기능 추가와 그 기능의 테스트·타입·스타일은 **같은 단위**로 묶는다.
- 서로 무관한 버그 수정, 리팩터링, 설정 변경은 **분리**한다.
- 한 파일 안에 성격이 다른 변경이 섞여 있으면 직접 판단한다. 대개는 그 파일의 주된 변경 단위에 넣고, 분리가 꼭 필요할 때만 hunk 단위로 나눈다. (대화형 플래그는 쓸 수 없으므로 패치 파일을 만들어 `git apply --cached`로 스테이징한다.)
- 단위가 하나뿐이면 억지로 쪼개지 않는다.

### 커밋에서 제외할 것

다음은 승인 없이 진행하더라도 **절대 자동으로 커밋하지 않는다.** 계획에서 빼고 결과 보고 때 이유와 함께 알린다.

- 비밀 정보가 담긴 파일: `.env`, `*.pem`, 키·토큰이 하드코딩된 변경 등
- 빌드 산출물·임시 파일: `dist/`, `node_modules/`, `*.log`, 디버그용 임시 파일
- `.gitignore`에 있어야 할 것으로 보이는 파일 (필요하면 `.gitignore` 추가를 별도 chore 단위로 제안)

## 3. 커밋 메시지 작성

형식:

```
<type>: <한국어 요약>

<본문 (선택): 무엇을, 왜 바꿨는지>
```

| type | 쓰는 경우 |
| --- | --- |
| `feat` | 사용자에게 보이는 새 기능·동작 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변화 없는 구조·코드 개선 |
| `chore` | 설정, 의존성, 빌드, 스킬·문서 등 그 외 작업 |

규칙:

- 요약은 50자 안팎, 마침표 없이, "~추가", "~수정", "~개선"처럼 명사형으로 끝낸다.
  - 좋음: `feat: 미리보기에 렌더링 크기 치수선 추가`
  - 나쁨: `feat: 수정함.`, `update files`, `feat: LivePreview.tsx 변경`
- 파일 이름이 아니라 **변경의 의미**를 쓴다.
- 요약만으로 이유가 드러나지 않으면 빈 줄 뒤에 본문을 2~4줄로 쓴다. 본문은 "왜"에 집중한다.
- 시스템이 지정한 커밋 attribution(예: `Co-Authored-By:` 줄)이 있으면 본문 끝에 빈 줄을 두고 붙인다. 프로젝트 지침(CLAUDE.md 등)이 다르게 정하면 그것을 따른다.
- `git log`의 기존 스타일이 이 컨벤션과 다르면 이 컨벤션을 따르되, 계획 제시 때 그 차이를 한 줄로 알린다.

## 4. 바로 커밋 (승인 단계 없음)

계획이 정해지면 사용자에게 묻지 않고 곧바로 5단계로 넘어간다. `AskUserQuestion`으로 승인을 받지 않는다.

- 단위 구분이나 메시지가 애매해도 묻지 않고 가장 합리적인 쪽으로 결정한다. 판단 근거는 결과 보고에 한 줄로 남긴다.
- 현재 브랜치가 `main`/`master` 같은 기본 브랜치여도 그대로 커밋하고, 결과 보고에 그 사실을 알린다.
- 예외: 사용자가 이번 요청에서 "확인하고 커밋해줘", "계획 먼저 보여줘"처럼 검토를 명시적으로 요청한 경우에만 계획을 보여주고 승인을 받은 뒤 커밋한다.

## 5. 커밋 실행

단위마다 순서대로:

```bash
git add -- <해당 단위의 파일들>     # 경로를 명시한다. git add -A / git add . 금지
git diff --staged --stat            # 의도한 파일만 올라갔는지 확인
git commit -F - <<'EOF'
<type>: <요약>

<본문>
EOF
```

- 첫 단위를 커밋하기 전에 사용자가 미리 스테이징해 둔 파일 중 그 단위에 속하지 않는 것은 `git restore --staged`로 내려 두고, 해당 단위 차례에 다시 올린다.
- pre-commit 훅이 실패하면 `--no-verify`로 우회하지 않는다. 그 단위에서 멈추고 실패 출력을 보여준 뒤, 원인을 고칠지 사용자에게 묻는다. (자동 진행은 정상 흐름에만 해당하며, 실패를 우회하지는 않는다.) 훅이 파일을 자동 수정했다면 그 변경을 다시 스테이징해 **새로** 커밋한다 (`--amend` 하지 않음).
- `git push`, `--amend`, `rebase`, `reset --hard`는 사용자가 따로 요청하지 않는 한 하지 않는다.

## 6. 결과 보고

승인 단계가 없으므로 보고가 사용자의 유일한 확인 수단이다. 모든 커밋이 끝나면 `git log --oneline -<커밋 수>`로 결과를 보여주고, 커밋별로 포함된 파일을 함께 적는다. 되돌리려면 `git reset --soft HEAD~<커밋 수>`를 쓰면 된다는 것도 알린다. 그리고 남은 미커밋 변경(제외한 파일 포함)이 있으면 함께 알린다. 실패한 단위가 있으면 어디까지 커밋됐고 무엇이 남았는지 분명히 적는다.
