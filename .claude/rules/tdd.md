# TDD Rule

> **이 규칙은 Rigid다. 상황에 맞게 변형하지 마라.**
> 아래 "적용 대상"에 해당하면 예외 없이 RED-GREEN-REFACTOR를 따른다. 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 0. 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 프로젝트 규칙이 없을 때 적용하는 **기본값(fallback)** 이다.
- 프로젝트 규칙이 일부만 다루면, 다루지 않는 부분에만 이 파일을 적용한다.
- 테스트 명령어는 프로젝트 문서에 적힌 것을 쓴다. (예: 이 저장소는 `bun run test`이고, `bun test`는 쓰지 않는다.)

## 1. 적용 기준

### TDD 필수

- **비즈니스 로직**: 규칙, 계산, 상태 전이, 분기 판단
- **API**: 라우트 핸들러, 요청 검증, 응답·에러 매핑
- **유틸 함수**: 파싱, 변환, 정규화, 포맷팅
- **버그 수정**: 버그를 재현하는 실패 테스트를 **먼저** 작성한다
- **커스텀 훅·상태 로직**: UI와 분리 가능한 동작

### TDD 불필요

- **타입 정의**: `interface`, `type`, 타입 전용 파일
- **설정 파일**: `vite.config.ts`, `tsconfig*.json`, ESLint, `package.json`
- **순수 UI**: 로직 없는 마크업, 스타일(CSS), 레이아웃, 문구 변경
- **SQL**: 스키마, 마이그레이션, 쿼리 파일 자체

판단이 애매하면 **필수로 간주**한다. 순수 UI 안에 분기·계산이 섞여 있으면 그 로직은 필수 대상이다. 로직을 함수나 훅으로 분리한 뒤 테스트한다.

## 2. RED-GREEN-REFACTOR

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 테스트 하나에 여러 동작을 검증하지 않는다.
- 테스트 이름은 검증하는 동작을 문장으로 쓴다. (예: `render 호출이 없으면 첫 컴포넌트에 주입한다`)
- **반드시 실행해서 실패를 눈으로 확인한다.** 실행하지 않은 테스트는 RED가 아니다.
- **실패 이유가 "기능 미구현"이어야 한다.** 오타, import 오류, 문법 오류, 잘못된 테스트 설정 때문에 실패했다면 RED가 아니다. 테스트를 고쳐서 올바른 이유로 실패하게 만든다.
- 처음부터 통과하는 테스트는 아무것도 증명하지 않는다. 테스트가 잘못됐거나 이미 구현된 동작이다. 원인을 확인한다.

### GREEN: 통과시키는 최소 코드

- **테스트를 통과시키는 최소한의 코드만 작성한다.**
- **YAGNI**: 지금 테스트가 요구하지 않는 분기, 옵션, 일반화, 에러 처리를 미리 넣지 않는다.
- 테스트를 수정해서 통과시키지 않는다. 바꿀 것은 프로덕션 코드다.
- **신규 테스트와 기존 테스트가 모두 통과하는지** 전체 테스트를 실행해 확인한다.

### REFACTOR: 구조 개선

- 대상: **중복 제거, 이름 개선, 헬퍼 추출**, 테스트 코드 정리.
- **매 변경 후 테스트를 실행해 green을 유지한다.** red가 되면 직전 변경을 되돌린다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 다음 사이클의 RED에서 시작한다.
- 개선할 것이 없으면 이 단계는 생략해도 된다. 생략은 허용되지만 새 동작 추가는 허용되지 않는다.

### 반복

- 다음 동작을 하나 골라 **RED로 돌아간다.**
- 한 사이클은 작게 유지한다. 테스트 하나와 그걸 통과시키는 코드 몇 줄이 기준이다.

## 3. 삭제 강제 규칙

- **테스트보다 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지한다.** 주석 처리, 별도 파일, 다른 브랜치, 스크래치 버퍼에 보관하는 것 모두 남기는 것에 해당한다.
- 삭제한 코드를 보면서 다시 타이핑하지 않는다. 테스트가 이끄는 대로 새로 작성한다.
- 이미 커밋된 코드에 테스트를 추가하는 경우는 이 규칙의 대상이 아니다. 단, 그 코드를 **수정**하려면 수정할 동작의 테스트를 먼저 작성한다.

## 4. 변명 차단표

| 변명 | 반론 |
| --- | --- |
| "너무 단순해서 테스트가 필요 없다" | 단순하면 테스트도 1분이면 끝난다. 단순해 보이는 코드가 경계값, 빈 입력, null에서 깨진다. **단순함은 생략 사유가 아니라 빨리 끝낼 수 있다는 뜻이다.** |
| "테스트는 나중에 추가하겠다" | 나중에 쓴 테스트는 구현을 따라 쓰게 되어 실패를 본 적이 없다. 이미 통과하는 테스트는 아무것도 증명하지 못한다. **나중은 오지 않는다.** |
| "시간이 없다" | 테스트 없이 아끼는 시간은 디버깅과 회귀 수정으로 더 크게 돌아온다. 시간이 없을수록 **되돌아가지 않는 경로**가 필요하다. |
| "이미 짠 코드를 삭제하면 낭비다" | 이미 쓴 시간은 돌아오지 않는다(매몰 비용). 테스트 없이 짠 코드를 지키면 검증되지 않은 설계가 남는다. **삭제하고 다시 짜는 쪽이 더 빠르고 더 작다.** |
| "프로토타입이라 괜찮다" | 프로토타입은 거의 항상 프로덕션으로 간다. 진짜 버릴 코드라면 적용 대상 밖의 별도 스파이크로 만들고 **결과물을 전부 버린다.** 남길 코드라면 TDD 대상이다. |

## 5. 완료 조건

다음을 모두 만족해야 작업을 완료로 보고한다.

- 추가하거나 수정한 모든 동작에 대해 **실패를 확인한 테스트**가 있다.
- 전체 테스트가 통과한다. 실행 결과(통과·실패 수)를 보고에 포함한다.
- 테스트 없이 남은 프로덕션 코드가 없다. 적용 불필요 대상이라면 그 사유를 보고에 적는다.
